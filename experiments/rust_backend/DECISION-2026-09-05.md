## Decision

Tiki assigns CUDA resource ownership and asynchronous execution to a Rust
runtime. It retains the CuTe MLIR compiler and uses CXX to connect the existing
MLX C++ core to a limited interface of opaque runtime objects.

CuTile Rust's host runtime components are candidates for reuse after ownership
qualification. The evaluated revision is not approved for unmodified adoption.
Crubit is not selected for the current interoperability boundary.

This record establishes the architecture and the evidence supporting it as of
the decision date. Implementation status is maintained in the
[backend overview](README.md#implementation-status). Findings are specific to
the evaluated revisions; they make no claim about subsequent upstream changes.

## Context and decision drivers

Tiki combines MLX tensor semantics and differentiation with explicit CUDA
kernel scheduling. Its existing compiler emits CuTe MLIR and produces CUDA
device binaries. The runtime must manage the lifetime and ordering of the
resources those binaries use.

Device execution can outlive a host call, a borrowed argument, or a cancelled
future. CUDA graph replay further extends resource lifetime beyond capture.
The architecture must make these obligations enforceable without coupling
model code to driver pointers or compiler implementation details.

The decision is based on four requirements:

1. Give each resource one ownership authority through completion and retirement.
2. Keep permitted memory access explicit across views, streams, and graph replay.
3. Preserve the existing compiler's control over kernel layout and scheduling.
4. Limit C++/Rust compatibility obligations to a stable subsystem boundary.

## Rationale

### Rust for host ownership and execution

Rust supports resource owners, scoped borrowing, explicit state transitions,
and a restricted unsafe interface to CUDA. Tiki can use these mechanisms to
make allocation, submission, and retirement part of one checked host API.
The same design applies to modules, execution handles, workspaces, and host
transfer destinations.

The choice does not require a Rust GPU kernel language. The CuTe compiler can
continue producing device code while Rust owns its execution. C++ remains a
viable implementation language for these contracts; Rust is selected to reduce
reliance on manually maintained lifetime conventions across call sites.
The [architecture specification](ARCHITECTURE.md#rust-implementation-model)
defines the selected Rust model and its limits.

### CXX for the interoperability boundary

Tiki requires explicit operations over opaque Rust owners, rather than broad
C++ access to the Rust runtime's implementation. CXX supports that interface
without exposing Rust field layout to C++.

Bridge definitions belong in the crate that owns the exposed types. This
avoids redundant wrapper types and keeps the ownership implementation and
foreign interface subject to the same review. CXX's representation checks
complement the runtime's lifetime contracts; they do not prove CUDA ordering.

### Preserve the CuTe artifact boundary

Tiki's compiler and runtime have independent responsibilities. The compiler
defines the kernel schedule and emits code; the runtime validates arguments,
orders access, and retains resources. Their shared artifact contract allows
either implementation to change without requiring a rewrite of the other.
The existing [compiler connection evidence](../cute_backend/GH200_PROOF.md)
establishes this separation.

CuTile Rust's CUDA Tile IR and Tiki's CuTe MLIR are distinct compiler targets.
Reuse of cuTile host runtime components does not require adoption of its
kernel language or replacement of the current compiler.

## Alternatives considered

| Alternative | Disposition | Reason |
| --- | --- | --- |
| Retain C++ ownership throughout the CUDA runtime | Retained during migration | Preserves existing execution while Rust ownership contracts are introduced at defined boundaries. |
| Adopt the evaluated cuTile Rust runtime without modification | Deferred | The graph-lifetime defect in F-01 violates a required ownership invariant. |
| Replace CuTe compilation with cuTile Rust kernel compilation | Not selected | Changing host ownership does not require changing the established compiler boundary; equivalent kernel coverage and performance have not been demonstrated. |
| Use Crubit for the C++/Rust boundary | Deferred | Generation works, but its representation and toolchain coupling exceed the requirements of the selected interface. |

## Evaluation findings

### F-01: cuTile scoped graph resource lifetime

At the evaluated revision, `CudaGraph::scope` returns `CudaGraph<()>` without
retaining the borrowed input allocation or expressing the graph's dependency
on its lifetime. `Scope::record` consumes the operation and releases its
borrows, while later replay uses the recorded device addresses.

The reproduction captures a prefix sum over `0..127`, drops the input, and
allocates replacement buffers until the allocator reuses the exact captured
address. After that replacement is filled with `1000`, graph replay returns
prefix values with endpoints `1000` and `128000`, rather than `0` and `8128`.

All application call sites use the safe Rust API. The compiler accepts the
program, and the GPU consumes replacement data without an API error. Retaining
the original input produces the correct result. A test that does not force
address reuse can pass despite the invalid lifetime.

This is a reproduced correctness defect in scoped capture and subsequent
replay. It does not establish that every cuTile operation is defective.
The source is
[`cuda-async/src/cuda_graph.rs`](https://github.com/NVlabs/cutile-rs/blob/7f606336e3e8dffa0e1ca3920844082afebb6810/cuda-async/src/cuda_graph.rs);
the [reproduction procedure](repros/README.md#cutile-scoped-graph-lifetime)
provides the pinned program and expected results.

### F-02: CXX ownership and type placement

The CXX control passes construction, mutation, and ownership transfer between
C++ and Rust. The generated C++ interface compiles with
`-Wall -Wextra -Werror`.

Declaring an opaque Rust type owned by a sibling crate in the bridge produces
`E0117`: generated trait implementations violate Rust's orphan rules.
A local newtype resolves the tested case. Defining the bridge with its owning
type removes the need for that adapter.

This is an integration constraint, not an observed memory-safety defect.
The [CXX procedures](repros/README.md#cxx-ownership-and-external-type-constraint)
include the working control and the intentional compile failure.

### F-03: Crubit generation and integration

The Cargo generator produces a C++ API directly from the original Rust
fixture. A C++ client constructs, mutates, and destroys the Rust buffer without
handwritten binding signatures. No memory-corruption defect in Crubit is
demonstrated.

The generated relocation code and support headers produce
`-Wnontrivial-memcall` diagnostics with Apple Clang 21.0.0. A build with
`-Werror` fails; adding `-Wno-nontrivial-memcall` permits compilation and
execution. The diagnostic does not itself establish incorrect relocation.
The [pinned-header procedure](repros/README.md#crubit-generated-header-diagnostics)
reproduces this build constraint.

The evaluation also identifies the following compatibility costs:

- Generator builds require nightly Rust and `rustc-dev`; the local macOS
  binary requires `librustc_driver` on its library search path.
- The generated fixture includes the private Rust `Vec<f32>` representation
  and relocation support in its C++ definition.
- The fixture has no ordinary C++ move constructor. By-value parameters use
  Crubit's `rs::Movable` protocol.

The revision includes
[Cargo tooling](https://github.com/google/crubit/tree/6e856fe23f0dc6755ee394ead76d4c7894091015/cargo/cc_bindings_from_rs)
and experimental
[Corrosion/CMake examples](https://github.com/google/crubit/tree/6e856fe23f0dc6755ee394ead76d4c7894091015/examples/build_systems/cmake_demo).
The assessment covers Cargo generation and the linked C++ client. The CMake
example is inspected but not executed; its integration remains unverified.

## Consequences and acceptance criteria

Tiki owns its runtime interface independently of an upstream implementation.
C++ callers receive opaque runtime owners and cannot rely on their Rust field
layout. Kernel compilation remains independent of host resource ownership.

CuTile runtime components require a reviewed, pinned revision that satisfies
the [resource and access contracts](ARCHITECTURE.md#resource-and-access-contracts).
Qualification must verify retained bindings and access ordering through graph
replay, early future drop, partial submission failure, and cache eviction.
F-01 must either return correct data after caller drop or reject the invalid
lifetime before execution.

Reconsider Crubit if the required foreign interface becomes substantially
broader and a representative integration demonstrates a lower total
maintenance cost. Reconsider kernel-language selection through a separate
decision with matched workload, correctness, and performance evidence.

The recorded interop procedures use host-only fixtures. The GPU procedure
covers a 128-element sum scan and explicit reverse-scan backward. These results
support the stated compatibility and lifetime findings; they do not qualify
a complete runtime or establish a performance ranking among the alternatives.
