## Decision

Tiki is memory safe from its Python API to the GPU. Rust owns every line of
host code: the graph, operators, differentiation, compilation, allocation,
streams, launches, file loading, and distributed communication. Rust also
owns every GPU memory address. The Python API stays the same.

GPU kernels are written in Tiki's own kernel language, which follows CuTe's
semantics: layouts as algebra, tensors, thread-value partitions, and copy and
MMA atoms. Tiki's compiler proves each kernel's memory accesses from that
algebra and lowers it through LLVM IR and LLVM's open NVPTX backend to PTX.

Everything on the execution path is Tiki's own code or open source, except a
vendor's user-space driver where no open one exists: `libcuda` on NVIDIA.
NVIDIA's closed libraries (the CUDA runtime, cuBLAS, NVRTC, `libNVVM`, CuTe DSL,
and cuTile) serve only as differential-testing oracles.

The revision changes four choices of the original decision:

- **Kernel language.** Tiki implements CuTe's semantics itself, in Rust with a
  Python frontend, from the BSD-3 CUTLASS sources. NVIDIA's CuTe DSL serves as
  a correctness and performance oracle only.
- **Compilation.** Tiki's compiler lowers kernels to LLVM IR and compiles them
  with upstream LLVM's NVPTX backend. The [CuTe MLIR experiments](https://github.com/dedalus-labs/tiki/tree/5555d20225b0befb21d7c56782384a20a1027b42/experiments/cute_backend)
  become its reference design.
- **Host runtime.** Tiki owns its host runtime. One `-sys` crate per target is
  the only call site into the vendor driver and the only Tiki code with
  `unsafe`: `tiki-cuda-sys` holds declarations generated from `cuda.h` and
  safe types over them. Streams, events, and device memory are owned values,
  and no address or handle crosses the crate as an integer, so safe code
  cannot name memory it does not own. Every other crate forbids `unsafe`.
- **Replacement.** The Rust stack is built beside the C++ backend, with its own
  entry points and no C++/Rust bridge. Differential tests run the Python suite
  on both until the Rust stack matches in results, features, and performance.
  One cutover then deletes the C++ backend.

## Context

The C++ runtime inherited from upstream MLX keeps producing one class of bug. In
[#1](https://github.com/dedalus-labs/tiki/pull/1), a NumPy export copied device
memory on one CUDA stream and freed the source on another. Nothing ordered the
free after the copy, and Compute Sanitizer reported a use-after-free on every
export.

The same class recurs across the codebase:

- [#47](https://github.com/dedalus-labs/tiki/pull/47): a strided view read four
  values of a freed array from a recycled allocation.
- [#62](https://github.com/dedalus-labs/tiki/pull/62): rejecting a view
  destroyed a buffer while an asynchronous copy still wrote to it.
- [#63](https://github.com/dedalus-labs/tiki/pull/63) and
  [#53](https://github.com/dedalus-labs/tiki/pull/53): misaligned storage
  reinterpretation and short file reads.

Each fix closes one instance. The class persists while C++ owns memory,
because every call site must remember the same rules. Rust ownership and a
checked tensor type make those rules part of the type system.

## Boundary

One rule places every piece of code:

1. **Runs on the CPU.** Rust.
2. **Computes a GPU address.** A layout in Tiki's kernel language, proven in
   bounds by the compiler.
3. **Runs on the GPU.** A kernel in Tiki's kernel language.
4. **Inherited CUDA C++ kernels.** Stay in the C++ backend, which the cutover
   deletes.
5. **Tensor-core GEMMs that Tiki kernels do not yet match.** CUTLASS, which
   computes its own addresses from checked inputs.

```mermaid
flowchart TB
    python[Python: Tiki API and tk kernel language] --> core[Rust core: graph, operators, autodiff]
    core --> compiler[Rust compiler: kernel IR, proofs, LLVM IR]
    compiler --> nvvm[LLVM NVPTX: LLVM IR to PTX]
    core --> runtime[Rust runtime: memory, streams, typed launches]
    nvvm --> runtime
    runtime --> kernels[Tiki kernels]
    kernels --> gpu[GPU memory]
```

## Compilation and execution

Compiling a kernel and running it are separate steps, and only running
touches the driver.

- **Compilation** is ordinary Rust. `tiki-compile` traces a kernel, proves it
  with `tiki-cute`, and lowers it to LLVM IR. LLVM's NVPTX backend writes PTX.
  No driver call and no `unsafe` take part.
- **Execution** goes through `libcuda`, the user-space interface to NVIDIA's
  kernel driver. Loading PTX, allocating device memory, copying, launching,
  and waiting are driver calls, and every call into C is `unsafe` in Rust.
  `tiki-cuda-sys` confines those calls, as the C library confines system calls
  under Rust's standard library.

A kernel is safe when its proofs hold and the lowering preserves them. Host
code is safe when the types `tiki-cuda-sys` hands out admit no misuse.
[From tk to PTX](../../docs/src/dev/kernels.rst#from-tk-to-ptx) follows one
kernel through every stage.

## Kernel language

Tiki needs thread-level control. Fast kernels choose how threads share work,
stage data through swizzled shared memory, and issue tensor-core and bulk-copy
instructions. CuTe expresses those choices as layouts, and its layout algebra
makes each choice composable and checkable.

The kernel language has two users. Researchers write kernels directly with
`@tk.kernel`, using layouts, tensors, thread-value partitions, and atoms. The
compiler writes kernels for fused Tiki graph regions by choosing tiles and
partitions. Both paths produce the same kernel IR, pass the same proofs, and
lower the same way.

The compiler proves these properties of every kernel from its layouts:

- **Bounds.** The codomain of each thread's composed layout lies inside its
  tensor's allocation, whether the tensor lives in global memory, shared
  memory, or registers.
- **Disjoint writes.** Each thread writes shared memory through an injective
  partition, so no two threads write one element.
- **Barrier coverage.** A barrier or `mbarrier` wait separates every shared
  memory read from conflicting writes.
- **Uniform barriers.** Every thread of a block reaches each block-wide
  barrier. A barrier under a branch that only some threads take hangs the
  block or corrupts shared memory.

A kernel that fails a proof does not compile.

An index read from tensor data, as in a gather, a scatter, a paged-attention
block table, or expert routing, has no static proof. The compiler checks each
such index before the access. A failed check skips the access and sets the
launch's error word, which the completion runtime returns as a typed error, so
the process and its CUDA context stay usable.

Kernels lower in stages. The kernel IR partitions tiles across threads and
selects atoms per architecture. A thread IR turns layout evaluation into
integer arithmetic and unrolls static loops. LLVM IR in the NVVM IR 2.0 form
carries NVVM intrinsics and inline PTX for instructions that lack intrinsics.
LLVM's NVPTX backend produces PTX, and nvJitLink or the driver produces the GPU
binary.

The proofs hold for the kernel IR, and the lowering keeps them true in LLVM IR:

- **Index width.** The proofs compute offsets as exact integers. The lowering
  uses 32-bit arithmetic only where the proof bounds every offset below 2^31,
  and 64-bit arithmetic elsewhere.
- **Flags from facts.** LLVM's `nsw`, `nuw`, `inbounds`, `noalias`, and
  alignment let it delete code that a false assumption makes dead, bounds
  checks included (F-06). The lowering emits each one only from a proven fact,
  or for `noalias` from the launcher's `&` and `&mut` borrows.
- **Floor division.** The algebra divides with floor division. LLVM's `sdiv`
  and `srem` round toward zero, so the lowering emits floor division for any
  operand that can be negative.
- **Launch facts.** A kernel runs only on arguments that satisfy the facts its
  proofs assumed, including a kernel that shapeless compilation reuses across
  shapes.

Extents are traced as static or dynamic. A static extent, such as a tile size,
becomes a constant the compiler folds, so bounds within a tile follow from
arithmetic. A dynamic extent, such as a sequence length, becomes a kernel
parameter, a polynomial variable whose facts, positivity and a divisor, the
kernel declares. The algebra decides each precondition from those facts and
refuses a kernel whose layout depends on a condition they leave open. At
launch, the runtime checks the grid size and each tensor's shape against the
kernel's contract, which are the facts the proof assumed.

A partial tile at the end of a dynamic mode is safe to read whole when the
tile stays inside the tensor's allocation, and reading it unmasked is often
faster than masking every load. The bounds proof covers the allocation. The
compiler generates the boundary mask for each dynamic mode, and a value proof
keeps every lane past the logical extent out of the kernel's results.

Layouts are data inside the compiler, with each extent tagged static or
dynamic. The algebra runs as ordinary code during compilation and never
through the host language's type system, so compiling a kernel costs
milliseconds before LLVM runs.

The layout algebra follows the CuTe whitepaper
([Cecka, arXiv:2603.02298](https://arxiv.org/abs/2603.02298)), which defines
every operation and post-condition. `tiki-cute` reproduces every integer call
in the test suite of NVIDIA's Apache-2.0 reference implementation,
[PyCuTe](https://github.com/NVlabs/CuTe/tree/111253d17e2f0f8631f43999b43ac4afa5954b04).
It also checks the whitepaper's condition for composing a hierarchical layout
mode by mode (Equation 23), which PyCuTe skips, so it refuses compositions
whose summed modes carry across a mode of the left layout.

The atom table holds each architecture's copy and MMA instructions: vectorized
loads, `cp.async`, and `mma.sync` from Ampere, TMA and `wgmma` from Hopper, and
`tcgen05` from Blackwell. Its PTX comes from CuTe's BSD-3 architecture headers
with attribution. Partitioning, tiled copies and MMAs, and pipeline patterns
follow CuTe's and CUTLASS's BSD-3 C++ sources.

## Apple GPUs

Tiki also targets Apple GPUs through Metal. The kernel IR and thread IR are
target-neutral: layouts, partitions, proofs, and per-thread arithmetic are the
same for both targets. Only atom selection and the final emitter depend on the
target.

| CUDA | Metal |
| --- | --- |
| Thread block | Threadgroup |
| Warp | SIMD-group |
| Shared memory | Threadgroup memory |
| `mma.sync`, `wgmma`, `tcgen05` | `simdgroup_matrix` |
| LLVM IR, NVPTX, `ptxas` | Metal Shading Language, Apple compiler |

The Metal emitter writes Metal Shading Language source, compiled by Apple's
compiler ahead of time into a `.metallib` or at load time from source, as Tiki
does. Metal has no bulk-copy or `mbarrier` hardware, so its pipelines use
threadgroup barriers. Tiki's MIT-licensed Metal kernels are the reference for
Apple tile shapes and `simdgroup_matrix` use.

## Launch and access

Every kernel has a declared Rust signature, and a generated launcher is the
only way to run it. The launcher accepts only checked tensors, takes outputs
by `&mut` so no two launches write one array at once, and retains each
argument's storage until the device reports completion.

The runtime's types carry the same rules outside launches. Device memory owns
its bytes and remembers the stream of its last write and the streams that
read it since. A copy or launch on another stream waits for them through an
event recorded at that moment, so work on one stream pays nothing for the
ordering. Every copy checks lengths, a read returns host values only after the
device finishes, and dropping memory frees it after every stream that used
it. Element types have no invalid bit patterns, so any bytes the
device writes are valid values.

At module load, the runtime compares each declared signature with the
parameter offsets and sizes that `cuFuncGetParamInfo` reports for the compiled
kernel. A mismatch fails before any launch.

One function pushes a device pointer into a launch, inside `unsafe`. Its
safety argument rests on three facts established elsewhere:

- The tensor passed `Tensor::new`, so every address it describes lies in its
  storage.
- The storage stays retained until the submission completes.
- The declared signature matched the kernel at load.

Inherited C++ kernels receive opaque tensor handles. A handle's bytes contain the device
pointer, and C++ cannot read them without a cast that the lint rejects. Every
load and store calls a Rust device function, compiled to LTO-IR and inlined
into the C++ kernel by nvJitLink. cuda-oxide demonstrates this link in its
[`cpp_consumes_rust_device`](https://github.com/NVlabs/cuda-oxide/tree/ec4aa47/crates/rustc-codegen-cuda/examples/cpp_consumes_rust_device)
example on Blackwell. Architectures without that LTO-IR path use a C++
accessor header whose formula is property-tested against the Rust definition.

## Enforcement

Tiki kernels carry their proofs from compilation. Further checks keep the
boundary in place:

- **Unsafe check.** Every Tiki crate except the per-target `-sys` crates
  declares `#![forbid(unsafe_code)]`, and CI rejects any other `unsafe`.
- **Source lint.** `clang-tidy` rejects pointer arithmetic in inherited kernel
  sources and any cast of an opaque tensor handle.
- **Sanitizers.** A merge-queue lane runs Compute Sanitizer's `memcheck` with
  leak checking and `racecheck` over the Python suite. PTX schedule
  perturbation from cuda-oxide's `ptx-schedule` widens the race search.
- **Differential tests.** Each Python test runs on the C++ backend and on the
  Rust stack, and their results must match. Closed NVIDIA libraries serve as
  further oracles for individual kernels.
- **Lowering tests.** Property tests compare the lowered index arithmetic with
  `tiki-cute` at negative coordinates and at offsets near 2^31 and 2^32.
  `libNVVM` compiles the same LLVM IR, and both binaries must agree.

The Python kernel language traces into `tiki-compile`. The Rust stack has its
own PyO3 bindings behind the same Python API, which is what the differential
tests run. `tiki-compile` loads
a pinned LLVM in a separate compiler process, so a compiler
failure ends one compilation with a typed error and never touches runtime
memory.

## Alternatives considered

**Fix each bug in C++.** Rejected. The same ownership mistake recurs at each
call site that handles memory, as #1, #47, and #62 show.

**Stop at NVIDIA's CuTe DSL.** Rejected. Its license is a revocable NVIDIA
EULA that forbids reverse engineering its compiler and restricts derivative
works, so Tiki could not fix, fork, or ship its kernel compiler. Its layout
algebra and atoms are available under BSD-3 in CUTLASS, and Tiki implements
them from there.

**Lower kernels to CUDA Tile IR.** Not selected as the kernel target. Tile IR
has no thread index, warp, or shared memory operations, so it cannot express
the thread-level control Tiki's kernels need. It also offers raw pointer
operations beside its bounded views.

**Rewrite kernels in cuda-oxide.** Not selected. cuda-oxide is an early alpha
on a pinned nightly toolchain, and its shared memory requires `unsafe`. Tiki
uses its PTX tooling and its Rust device interop for inherited C++ kernels.

**Compile with NVIDIA's `libNVVM`.** Not selected as the code generator.
`libNVVM` runs the same device optimizer as `nvcc`, but it is closed, so Tiki
could not read, fix, or upstream changes to it. LLVM's NVPTX backend accepts the
same LLVM IR, and Tiki pins and vendors LLVM when a fix must ship before it
lands upstream. Tiki's atoms are inline PTX, so new hardware instructions do not
wait for NVPTX intrinsics. `libNVVM` compiles the same IR in CI as a
differential check.

**Crubit for the C++/Rust boundary.** Not selected. F-03 records its toolchain
and representation costs.

**Port the C++ backend in place through a CXX bridge.** Tried and reverted. A
Rust allocator under the C++ backend (#8, #96) ran one backend in two
languages, with a seam between them that neither side's tests owned. The
parallel build has no bridge.

**cuTile Rust host crates.** Not selected. Their allocation, copy, advice, and
launch functions are `pub unsafe fn`, so every caller writes `unsafe`, and the
project is NVIDIA-owned and pre-1.0. Tiki's host layer wraps the driver itself
and exports only safe functions.

## Evaluation findings

### F-01: cuTile scoped graph resource lifetime at `7f606336`

At this revision, `CudaGraph::scope` returns `CudaGraph<()>` without retaining
the borrowed input allocation. `Scope::record` consumes the operation and
releases its borrows, while later replay uses the recorded device addresses.

The reproduction captures a prefix sum over `0..127`, drops the input, and
allocates replacement buffers until the allocator reuses the captured address.
After that replacement is filled with `1000`, replay returns prefix values with
endpoints `1000` and `128000`, where `0` and `8128` are correct.

Every call site uses the safe Rust API, and the GPU consumes the replacement
data without an error. A test that does not force address reuse passes despite
the invalid lifetime. The
[reproduction procedure](repros/README.md#cutile-scoped-graph-lifetime) pins the
program and its expected results.

### F-02: CXX ownership and type placement

Construction, mutation, and ownership transfer pass between C++ and Rust, and
the generated C++ interface compiles with `-Wall -Wextra -Werror`.

Declaring an opaque Rust type owned by a sibling crate in the bridge produces
`E0117`, because the generated trait implementations violate Rust's orphan
rules. Defining the bridge beside its owning type avoids the adapter. The
[CXX procedures](repros/README.md#cxx-ownership-and-external-type-constraint)
include the working control and the intentional compile failure.

### F-03: Crubit generation and integration

The Cargo generator produces a C++ API directly from the Rust fixture, and a
C++ client constructs, mutates, and destroys the Rust buffer without
handwritten binding signatures.

The generated relocation code produces `-Wnontrivial-memcall` diagnostics with
Apple Clang 21.0.0, so a build with `-Werror` fails until
`-Wno-nontrivial-memcall` is added. Generator builds require nightly Rust and
`rustc-dev`. The generated fixture exposes the private `Vec<f32>`
representation to C++ and passes values through Crubit's `rs::Movable`
protocol. The
[pinned-header procedure](repros/README.md#crubit-generated-header-diagnostics)
reproduces the build constraint.

### F-04: cuTile 0.4.0 graph ownership

At 0.4.0, an instantiated graph takes ownership of its capture context and
recorded resources and keeps them until the graph is destroyed. The F-01
program, extended to replay after dropping its input, allocated 4,096
same-sized buffers without receiving the captured address, and replay read
the original input. Compute Sanitizer's `memcheck` reported zero errors.

`drop(input)` still compiles while the graph holds a capture of it. Safety
comes from the runtime retaining the buffer, and the borrow checker does not
reject the drop.
[#69](https://github.com/dedalus-labs/tiki/issues/69) records the run.

### F-05: Integer handles in the host adapter

The first `tiki-cuda-sys` adapter typed addresses and streams as `usize` and
exposed its driver calls as safe functions. A caller that forbids `unsafe`
changed an immutable vector on a GH200:

```rust
#![forbid(unsafe_code)]
let frozen: Vec<u8> = vec![0; 16];
let source: Vec<u8> = vec![7; 16];
driver::memcpy_async(frozen.as_ptr() as usize, source.as_ptr() as usize, 16, stream)?;
```

After the copy, `frozen` held sixteen 7s. The same signatures admitted use
after free, double free, and copies past either buffer. A safe wrapper is only
as sound as the types it accepts, so the adapter now hands out owned values,
and a compile-fail test keeps this program rejected.

### F-06: An unproven `nsw` deletes a bounds guard

An offset `row * 65536 + col` lowered as 32-bit arithmetic with `nsw`, guarded
by `0 <= offset < len`. `opt -O2` from LLVM 21.1.8 and 23.1.2 removed the
`offset >= 0` check, because `nsw` declares that the arithmetic never wraps.
At `row = 32768` the product wraps to -2^31, passes `offset < len`, and
becomes +2^31 after `zext nneg`. On macOS arm64 the store landed 8 GiB past a
16-element buffer and the process received `SIGSEGV`. The same IR without
`nsw` kept both checks and rejected the store. The
[reproduction procedure](repros/README.md#unproven-nsw-bounds-guard) pins both
programs.

## Consequences

The replacement proceeds in order, tracked by
[#65](https://github.com/dedalus-labs/tiki/issues/65):

1. Strengthen the Python test contract and run it on both backends.
2. Build the Rust stack beside the C++ backend: runtime, compiler, kernels,
   and PyO3 bindings.
3. Run the differential suite until the Rust stack matches the C++ backend.
4. Cut over in one change that deletes the C++ backend.

The cutover requires the Python suite to pass on the Rust stack with results
matching the C++ backend, zero `memcheck` and `racecheck` errors, and device
time within 5% of the C++ backend.

Tiki pins every oracle (CuTe DSL, cuTile, `libNVVM`) and tool (cuda-oxide's
PTX tooling) to an exact version or commit. An upgrade reruns the
qualification suite before it lands.
